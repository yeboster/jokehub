## 1. GENERAL / CODE QUALITY

### 1.1 — `deleteJoke` batch will be rejected once rules are deployed
**`src/services/jokeService.ts:247-267`** + **`firestore.rules:111`**

`deleteJoke` queries every `jokeRatings` doc for the joke and batch-deletes them alongside the joke. The rule allows deleting a rating only when `resource.data.userId == request.auth.uid`. A joke rated by anyone else therefore contains rating docs the owner may not delete, and because a `writeBatch` is atomic, one denial rejects the entire commit — the joke is **not** deleted either.

**Why it matters:** rules are not yet deployed (per `PROJECT_PROGRESS.md`), so this is latent and lands the moment `npm run firestore:deploy` runs. Delete silently fails for exactly the popular jokes users most want to remove.

**Fix:** add an owner branch to the ratings delete rule:
```
allow delete: if request.auth != null && (
  resource.data.userId == request.auth.uid ||
  get(/databases/$(database)/documents/jokes/$(resource.data.jokeId)).data.userId == request.auth.uid
);
```
Or move joke deletion to an Admin-SDK API route. Also chunk the batch at 500 writes — Firestore's hard batch limit is exceeded by a joke with 500+ ratings.

### 1.2 — Every filtered `/jokes` query needs a composite index that isn't declared, and has no fallback
**`src/services/jokeService.ts:39-107`**, **`firestore.indexes.json`**

`buildJokesQuery` composes up to four equality filters (`userId`, `keywords array-contains`, `category in`, `funnyRate`, `used`) plus `orderBy('dateAdded','desc')`. Every one of those combinations requires a composite index. `firestore.indexes.json` declares only two `jokeRatings` indexes — nothing for `jokes`. Unlike `fetchUserFiveStarJokes` and `fetchAllRatingsForJoke`, `fetchJokes` has no `isMissingIndexError` fallback, so it throws straight to the error toast.

**Why it matters:** "My Jokes", every category filter, the rating filter, the used/unused filter and search are all broken in production until the indexes exist. The unfiltered public feed works, which is why this hides well.

**Fix:** add `jokes` composite indexes to `firestore.indexes.json` (at minimum `userId+dateAdded`, `category+dateAdded`, `used+dateAdded`, `funnyRate+dateAdded`, `keywords+dateAdded`, and `userId+used+dateAdded`), deploy, and wrap `fetchJokes`'s `getDocs` in the same `isMissingIndexError` → drop-`orderBy`-and-sort-client-side fallback the rating queries already use.

### 1.3 — Both AI routes are unauthenticated; `explain-joke` writes to an arbitrary joke doc
**`src/app/api/explain-joke/route.ts:13-60`**, **`src/app/api/generate-joke/route.ts:112`**

Neither route calls `verifyApiToken` (which `/api/jokes/add` and `/api/jokes/top` do). Anyone can POST to `/api/generate-joke` and trigger two Gemini calls (6 candidates + critic) with a caller-chosen model and temperature. `/api/explain-joke` is worse: it accepts any `jokeId` plus any `jokeText`, and at line 52-59 writes the model output to `jokes/{jokeId}.explanation` through the **Admin SDK, bypassing security rules entirely** — with no existence check and no ownership check.

**Why it matters:** unmetered LLM billing on public endpoints, and any anonymous caller can overwrite the explanation on every joke in the database with attacker-supplied text.

**Fix:** require a Firebase ID token (verify via `getAuth().verifyIdToken`) or the shared API token on both routes, and add per-IP/per-user rate limiting. In `explain-joke`, load the joke server-side and explain *its stored text* rather than caller-supplied `jokeText`; drop `jokeText` from the request schema. Separately, `verifyApiToken` (`src/lib/auth.ts:23-27`) uses `token !== API_TOKEN` — switch to `crypto.timingSafeEqual` and parse the header with a `^Bearer\s+` regex instead of `replace('Bearer ', '')`.

### 1.4 — An explanation is generated automatically on every joke view
**`src/app/joke/[jokeId]/page.tsx:127-129`**

Whenever a joke lacks a stored `explanation`, opening the detail page fires `streamExplanation` unprompted. The `useEffect` deps include `user`, so a login-state change re-runs it.

**Why it matters:** one LLM call per unexplained page view, including bots and crawlers; concurrent viewers each generate their own. The `ExplanationCard` already has an explicit "Explain again" button, so the interaction exists.

**Fix:** render a "Explain this joke" call-to-action when `explanation` is empty and only stream on click. Keep auto-display for jokes that already have a persisted explanation.

### 1.5 — Editing a joke leaves a stale AI explanation attached
**`src/services/jokeService.ts:231-234`**

`updateJoke` regenerates `keywords` when `text` changes but leaves `explanation` untouched. Because the detail page only regenerates when `explanation` is falsy, the old explanation sticks permanently to the new text.

**Why it matters:** users see an explanation of a joke that no longer exists, with no way to refresh short of clicking "Explain again."

**Fix:** in the `updatedData.text !== undefined` branch, also set `dataToUpdate.explanation = ''` (or `deleteField()`) when the text actually differs from the stored value.

### 1.6 — Any authenticated user can forge rating aggregates on any joke
**`firestore.rules:14-24`**

The second `canUpdateJoke` branch permits any signed-in user to write arbitrary numbers to `averageRating`, `ratingCount`, and `ratingSum` on any joke, with no cross-check against `jokeRatings`. It exists because `ratingService.submitUserRating` does the aggregation client-side.

**Why it matters:** the community rating — the main sorting/quality signal, and the input to the server-side exemplar fetch — is trivially forgeable with a direct SDK call. Nothing about the current rule constrains the values to the actual ratings.

**Fix:** move `submitUserRating` behind an authenticated API route using `adminDb.runTransaction`, then tighten the rule to `allow update: if <owner branch only>`. If keeping it client-side is a deliberate trade-off, at minimum bound the fields (`ratingCount == resource.data.ratingCount + 1 || == resource.data.ratingCount`, `averageRating >= 0 && <= 5`) and document the residual risk.

### 1.7 — `getJokeById` reads the same document twice
**`src/services/jokeService.ts:193-200`**

`getJokeDoc(jokeId)` already performs a `getDoc` and returns the snapshot data, but `getJokeById` discards it and issues a second `getDoc(ref)` on the same reference.

**Why it matters:** doubles the read cost of the joke detail page, the edit page, and the post-rating refetch — three of the hottest paths in the app.

**Fix:** return the `docSnap` from `getJokeDoc` and map it directly; delete the second `getDoc`.

### 1.8 — A joke with a missing `dateAdded` crashes the whole list
**`src/services/jokeService.ts:99`** (and **`:341`**)

`(docSnapshot.data().dateAdded as Timestamp).toDate()` is an unchecked cast inside `snapshot.docs.map`. `/api/jokes/add` writes `FieldValue.serverTimestamp()`, and migration-written or hand-edited docs may lack the field — any such doc throws `TypeError: toDate is not a function` and the entire `fetchJokes` call rejects.

**Why it matters:** one malformed document takes down the whole feed rather than degrading to one bad card.

**Fix:** a small `toDate(value)` helper returning `value instanceof Timestamp ? value.toDate() : new Date(0)`, applied in `fetchJokes`, `fetchTopJokes`, `getJokeById`, and `mapRatingDocs` (which has the same unchecked cast on `createdAt`/`updatedAt` at `ratingService.ts:150-151`).

### 1.9 — `/api/jokes/top` parses query params without radix, NaN guard, or clamp
**`src/app/api/jokes/top/route.ts:15-16`**

```ts
const limit = parseInt(searchParams.get('limit') || '10');
const minRating = parseFloat(searchParams.get('minRating') || '4');
```
`?limit=abc` yields `NaN`, which Firestore's `limit()` rejects with a 500. `?limit=100000` is honored in full.

**Fix:** `const limit = Math.min(Math.max(Number.parseInt(x ?? '10', 10) || 10, 1), 50)` and an equivalent 0–5 clamp for `minRating`, or validate both with a zod schema like the other routes do.

### 1.10 — `handleApiCall`'s auth bypass check can never match, and the error branch can throw
**`src/contexts/JokeContext.tsx:173`** and **`:194`**

```ts
if (!user && !['fetchAllRatingsForJoke', 'getJokeById'].includes(apiCall.name))
```
Every caller passes an inline arrow function as an argument, so `apiCall.name` is always `''` — the allow-list never matches and is pure misdirection (neither of those two functions routes through `handleApiCall` anyway). Line 194 then calls `err.message.includes(...)` unguarded, which throws a second `TypeError` if a non-`Error` is thrown, masking the original failure.

**Fix:** delete the `apiCall.name` list and make the guard a plain `if (!user)`. Guard the message read: `const message = err instanceof Error ? err.message : String(err)`.

### 1.11 — CSV import is all-or-nothing and can be rejected wholesale by the rules
**`src/components/csv-import.tsx:109-146`**, **`src/services/jokeService.ts:130-157`**, **`firestore.rules:46`**

Rows are collected client-side then written in a single `writeBatch`. The create rule requires `source.size() <= 100`; a single row with a longer source (or any other rule violation) rejects the entire batch. Skipped rows only produce `console.warn` — the success toast reports `importedJokes.length` regardless of what the batch actually did.

**Why it matters:** a user importing 200 jokes gets either everything or nothing, with a toast that says "200 joke(s) processed" even in failure-adjacent cases.

**Fix:** validate `source` length and trim/reject client-side before batching; chunk into ≤500-doc batches; collect skipped-row indices and surface them in the toast ("187 imported, 13 skipped — rows 4, 19, …").

### 1.12 — Dead code across the service and context layers
- `src/services/jokeService.ts:176-182` — `rateJoke`: no callers anywhere.
- `src/services/jokeService.ts:184-191` + `src/contexts/JokeContext.tsx:240-250,340` — `updateJokeCategory`: exposed on the context, consumed by nothing (the edit page uses `updateJoke`).
- `src/services/ratingService.ts:114-137` + `src/contexts/JokeContext.tsx:304-314,347` — `getUserRatingForJoke`: the detail page derives the current user's rating from `allRatings` instead.
- `src/lib/constants.ts:11` + `src/services/jokeService.ts:219` — `SYSTEM_USER_ID`: an ownership-check escape hatch in a **client-side** service that no caller uses; the underlying write is still rules-gated, so it's inert but misleadingly implies a server trust path exists.

**Why it matters:** ~90 lines of maintained-but-unreachable code, and the `SYSTEM_USER_ID` bypass reads like a security hole to anyone auditing the file.

**Fix:** delete all four, along with their `JokeContextProps` entries.

## 2. REFACTORING / ARCHITECTURE

### 2.1 — Two independent effects race to load the same joke list
**`src/contexts/JokeContext.tsx:147-164`**, **`src/app/jokes/page.tsx:110-118`**, **`src/app/page.tsx:28-38`**

`JokeProvider` runs its own effect that calls `loadJokesWithFilters(activeFiltersRef.current)` whenever auth or categories settle. Every consumer page *also* calls `loadJokesWithFilters` in its own effect. On `/jokes` both fire on mount — two identical paginated queries. On the home page the context fires the default filters while the page fires `limit: 3`, and whichever resolves last wins. `fetchJokesInternal` has no request-sequence guard, so a slow earlier response can overwrite a newer one after a rapid filter change. The detail and edit pages pay for a full list fetch they never render.

**Fix:** make fetching page-owned — delete the provider's auto-fetch effect and let each page declare what it needs. Add a monotonic request id in `fetchJokesInternal` and discard responses whose id is stale.

### 2.2 — `loadingInitialJokes` is aliased as the *categories* loading flag in four places
**`src/app/add-joke/page.tsx:28`**, **`src/app/edit-joke/[jokeId]/page.tsx:58`**, **`src/app/manage/page.tsx:24`**, **`src/components/add-joke-form.tsx:49`**

```ts
const { categories, loadingInitialJokes: loadingCategories } = useJokes();
```
The context has no categories-loading flag (it signals loading via `categories === null`), so consumers borrow the jokes flag. The category combobox is therefore disabled while *jokes* load and enabled while categories are genuinely still loading — showing "No personal categories found" and offering to create a duplicate.

**Fix:** add an explicit `loadingCategories: boolean` to `JokeContextProps`, set it in the subscription effect, and replace all four aliases.

### 2.3 — Submitting a rating triggers three round-trips
**`src/contexts/JokeContext.tsx:292-302`**, **`src/app/joke/[jokeId]/page.tsx:199-208`**

`submitUserRating` passes `shouldReloadJokesList = true`, refetching the paginated joke list the user isn't looking at. The detail page then separately refetches the joke doc *and* all ratings for the joke.

**Fix:** pass `false` for the list reload, and patch the single joke in the context's `jokes` array (as `toggleUsed` already does at `JokeContext.tsx:231-235`). The transaction already returns the new aggregate values — return them from `submitUserRating` and apply them locally instead of refetching the joke doc.

### 2.4 — A server route uses the client Firestore SDK
**`src/app/api/jokes/top/route.ts:2`** → **`src/services/jokeService.ts:321-345`**

`/api/jokes/top` is a token-authenticated server route, but `fetchTopJokes` imports `db` from `@/lib/firebase` (the browser SDK). It only works because `allow read: if true`; it runs unauthenticated against the rules, can't see anything a rule would restrict, and pulls the client SDK into the server bundle.

**Fix:** reimplement `fetchTopJokes` against `adminDb` in a `src/services/server/` module, matching the pattern already used by `/api/jokes/add` and `/api/explain-joke`.

### 2.5 — `/jokes` is a 543-line component holding four concerns
**`src/app/jokes/page.tsx`**

One component owns: URL↔filter serialization (`:61-140`), five pieces of duplicated `temp*` modal state (`:52-57`, reset identically at `:184-198` and `:262-269`), the entire filter dialog markup (`:283-457`), the active-filter badge row, and the list/pagination. Filter equality is done with `JSON.stringify(prev) === JSON.stringify(next)` (`:95`), which is key-order dependent. `defaultFilters` is defined twice with identical content (`JokeContext.tsx:38-44` and `jokes/page.tsx:24-30`).

**Fix:** extract `src/lib/jokeFilters.ts` (single `DEFAULT_FILTERS`, `parseFiltersFromParams`, `filtersToSearchParams`, `filtersEqual`), a `useJokeFilters()` hook wrapping the URL sync, and a `<JokeFilterDialog>` component taking `{ value, onApply }` — collapsing the five `temp*` states into one draft object. Target ~150 lines for the page.

### 2.6 — The creatable category combobox is duplicated verbatim
**`src/components/add-joke-form.tsx:106-128,159-230`** vs **`src/app/edit-joke/[jokeId]/page.tsx:169-190,259-293`**

`categoryNames`, `categoryOptions` (including the `Create "x"` unshift and case-insensitive exact-match test), and the ~60-line Popover/Command markup are near-identical. They've already drifted: the add form uses `<Command>` with default filtering while the edit page passes `shouldFilter={false}`, so the two search boxes behave differently.

**Fix:** extract `<CategoryCombobox value onChange disabled />` plus a `useUserCategories()` hook, and use it in both.

### 2.7 — Search only matches single whole words, silently
**`src/services/jokeService.ts:54-56`**, **`src/lib/text.ts:5-12`**

The query is `where('keywords', 'array-contains', filters.search.toLowerCase())`. `keywords` holds punctuation-stripped words longer than two characters. So `"fake spaghetti"` matches nothing (no keyword contains a space), `"atoms?"` matches nothing (the stored keyword is `atoms`), and `"an"` matches nothing (filtered at write time). The UI reports "No jokes found" with no explanation.

**Fix:** run the search term through `generateKeywords` and use the first token (or `array-contains-any` with up to 10 tokens, then intersect client-side). Update the placeholder to "Search by keyword…" and show "No jokes matched *word*" so the semantics are visible. Note that keyword search needs the composite indexes from §1.2.

### 2.8 — Test config excludes `.tsx`, and the highest-risk service is untested
**`vitest.config.mts`**

`include: ['src/**/*.test.ts']` means no component or hook test can ever be picked up. The 21 existing tests cover `ratingService.submitUserRating`, `verifyApiToken`, and `generateKeywords` — good choices — but `jokeService` (query construction, pagination, the `dateAdded` mapping of §1.8), the hand-rolled CSV parser (`csv-import.tsx:68-92`, quoting and escaped-quote handling), and the filter/URL serialization of §2.5 have no coverage.

**Fix:** widen to `src/**/*.test.{ts,tsx}` and add `environment: 'jsdom'` (a `jsdom` devDependency is needed). Prioritize pure-function tests first: extract `parseCSVLine` into `src/lib/csv.ts` and test it, then `buildJokesQuery`/`filtersToSearchParams`.

## 3. DESIGN / UI-UX

### 3.1 — Geist fonts are downloaded on every page and never used
**`src/app/layout.tsx:11-19,37`**, **`src/app/globals.css:5-7`**, **`tailwind.config.ts`**

`layout.tsx` loads `Geist` and `Geist_Mono` via `next/font/google` and puts `--font-geist-sans`/`--font-geist-mono` on `<body>`. But `globals.css` sets `body { font-family: Arial, Helvetica, sans-serif; }`, and `tailwind.config.ts` has no `fontFamily` extension mapping `sans` → `var(--font-geist-sans)`. Nothing consumes the variables.

**Why it matters:** the app renders in Arial while paying the download and layout cost of two web fonts — and the intended typography ("clean, organized, modern layout") never appears.

**Fix:** delete the `body { font-family: … }` rule and add to the Tailwind theme:
```ts
fontFamily: { sans: ['var(--font-geist-sans)', 'sans-serif'], mono: ['var(--font-geist-mono)', 'monospace'] }
```

### 3.2 — Theme tokens no longer match the documented style guide
**`src/app/globals.css:20,29`** vs **`context/PROJECT_CONTEXT_HISTORY.md:18-22`**

The guide specifies primary = dark gray `#333333`, secondary = medium gray `#666666`, accent = purple `#800080`. The implementation instead makes purple the *primary* (`--primary: 270 60% 50%`, ≈`#6A0DAD`) and a pastel purple the *accent* (`270 80% 95%`). `--foreground: 0 0% 20%` is `#333333` ✓, but `--muted-foreground: 0 0% 45.1%` is `#737373`, not `#666666` (`0 0% 40%`). The accent hue is 270°, not the 300° of `#800080`.

**Why it matters:** the guide is the reference for every future styling decision and for the design-review loop; a doc that contradicts the code makes both untrustworthy. The purple-primary choice looks deliberate and reads well — the doc is what's stale.

**Fix:** decide once and record it. Recommended: keep purple-primary, update `PROJECT_CONTEXT_HISTORY.md` §Styling Guidelines to describe the actual palette (purple primary `270 60% 50%`, gray text scale, pastel accent), and correct `--muted-foreground` to `0 0% 40%` to hit the specified `#666666`.

### 3.3 — Average ratings round up to full stars, and the default fill color is near-invisible
**`src/components/StarRating.tsx:37,56`**

`const isFilled = i < rating` means an average of `4.1` renders **five** filled stars — identical to a perfect 5.0. This affects every joke card (`joke-list-item.tsx:61-66`) and the detail page average (`CommunityRatings.tsx:42`), where the numeric `4.1` sits next to five full stars.

Separately, the default filled color is `text-accent` — in light mode `--accent` is `270 80% 95%` (near-white pastel), so a `<StarRating>` rendered without an explicit `starClassName` is effectively invisible on a white card. All three current call sites happen to pass `text-primary`, so the broken default is latent.

**Fix:** render partial fills (a clipped overlay star at `(rating % 1) * 100%` width), or at minimum `Math.round(rating * 2) / 2` with a half-star glyph. Change the default `starClassName` to `text-primary`.

### 3.4 — Every filter change blanks the entire `/jokes` page to a centered spinner
**`src/app/jokes/page.tsx:240-249`**, **`src/contexts/JokeContext.tsx:96-98`**

`fetchJokesInternal` sets `jokes` back to `null` on any non-load-more fetch, which makes `isPageLoading` true, which replaces the header, filter bar, and active-filter badges with a full-viewport "Loading jokes and categories…" spinner. Applying a filter therefore destroys the whole UI and rebuilds it.

**Why it matters:** the page visibly "jumps" on every interaction, scroll position is lost, and the user briefly can't see which filters they just applied.

**Fix:** keep the chrome mounted permanently; scope the loading state to the results grid and render 4–8 `<Card>` skeletons in the existing grid layout. Reserve the full-page spinner for the genuine first paint (`jokes === null && !hasFetchedOnce`).

### 3.5 — Home-page fallback jokes are fake and link to 404s
**`src/app/page.tsx:17-21,44-45`**

When the public feed returns nothing, `HARDCODED_JOKES_FALLBACK` renders three jokes with ids `hc1`/`hc2`/`hc3`. `JokeListItem` wraps its body in `<Link href={`/joke/${joke.id}`}>`, so clicking one navigates to `/joke/hc1` → "We couldn't find the joke you're looking for."

**Why it matters:** a new or empty deployment presents fabricated content as real, and every click is a dead end. The `else` branch at `:79-81` already has the correct copy ("No sample jokes to display right now") — it's just unreachable.

**Fix:** delete the fallback array and let the empty state render. If placeholder content is wanted for the marketing value, render it as non-interactive cards (no `Link`) with a "sample" badge.

### 3.6 — Hardcoded yellow alert boxes break in dark mode
**`src/components/add-joke-form.tsx:137`**, **`src/components/csv-import.tsx:208`**

```
bg-yellow-50 border-yellow-200 text-yellow-700
```
These are literal light-mode palette values in an app with a full dark theme (`globals.css:58-101`) and a working `<ThemeToggle>`. In dark mode a near-white block with mid-yellow text lands on a `0 0% 10%` background — jarring, and `text-yellow-700` on `bg-yellow-50` is the only place in the app not driven by theme tokens.

**Fix:** use the existing `<Alert>` component (`src/components/ui/alert.tsx`), or at minimum add `dark:` variants (`dark:bg-yellow-950 dark:border-yellow-900 dark:text-yellow-200`). The destructive-alert pattern used at `add-joke/page.tsx:157` (`bg-destructive/10 border-destructive/30 text-destructive`) is the token-driven idiom to follow.

### 3.7 — Nested interactive elements and noisy screen-reader output for read-only stars
**`src/app/jokes/page.tsx:354-369`**, **`src/components/StarRating.tsx:39-58`**

The category-removal control is a `<span role="button" tabIndex={0}>` rendered *inside* the `<Button role="combobox">` of the Popover trigger — nested interactive elements, which is invalid HTML and gives ambiguous behavior in screen readers and with keyboard traversal.

`StarRating` always renders `maxStars` separate `<Button>` elements. In read-only mode a screen reader announces five items ("Filled star 1 of 5", "Filled star 2 of 5", …) for what is semantically one value, on every card in the grid.

**Fix:** move the badge's remove action outside the trigger button (render selected categories as a separate row beneath it, each with its own `<button aria-label="Remove category X">`). In `StarRating`, when `readOnly` is true render a single `<div role="img" aria-label={`${rating} out of ${maxStars} stars`}>` containing plain `<Star>` icons with `aria-hidden`, and reserve the button-per-star markup for the interactive case.

## Recommended Execution Order

**Task 1 — Unblock production Firestore (highest risk, blocks everything else)**
§1.1 delete-rule conflict + batch chunking, §1.2 `jokes` composite indexes + `fetchJokes` fallback. Deploy rules and indexes, then verify each filter path in the UI. These two are the difference between "the app works" and "the app appears to work on the default feed only."

**Task 2 — Close the AI endpoints**
§1.3 auth + rate limiting on `/api/explain-joke` and `/api/generate-joke`, server-side joke text lookup, `timingSafeEqual` in `verifyApiToken`. §1.4 gate explanation generation behind an explicit click. Together these stop both the billing leak and the arbitrary-write path.

**Task 3 — Firestore correctness and cost**

**Task 4 — Delete dead code, then decide on rating integrity**
§1.12 remove `rateJoke`, `updateJokeCategory`, `getUserRatingForJoke`, `SYSTEM_USER_ID` (do this before refactoring so there's less surface to move). **Task 5 — Fix the fetch lifecycle**

**Task 6 — Decompose `/jokes` and de-duplicate**

**Task 7 — Design system pass**
